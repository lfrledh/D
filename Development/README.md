# Local development resources

Debug uses `Development.local.xcconfig` (ignored) to locate the verified local engine resource set and the already approved development signing identity. Prepare once using `scripts/prepare-development-resources.py`, then set `D_DEVELOPMENT_RESOURCES` to that absolute output directory. Set `D_DEVELOPMENT_SIGNING_IDENTITY` and `D_DEVELOPMENT_TEAM` only to your existing development identity. Do not put credentials in this file.

The normal D build validates the inventory, uses the native Xcode Resources copy phase, and then performs the ordinary Xcode signing step. Script sandboxing remains enabled; the validator writes no engine files. The resource set contains runtime code and, for the current internal Pitch engine, the explicitly tracked evaluation weight; it does not contain Qwen/FLUX/MRT2/Wan weights. This is a development configuration, not a distribution artifact. Missing or changed resource inputs fail with a preparation message rather than producing an app that appears ready.

Engine dependencies and model weights are not downloaded or installed by the resource-embedding build step. SwiftPM may resolve/fetch missing pinned packages during a normal build; the existing offline option requires a populated cache. Xcode owns and may replace the Engines directory in its current build output. Resource sources, model weights and other installed applications remain read-only; use an independent task-owned DerivedData directory.

For the isolated development trial, choose the shared **D Nodes** scheme and **My Mac**. It runs the same Debug D target with a fixed `D_UI_TEST_SESSION` value, isolating the model index and preferences from ordinary D while preserving the trial across launches. It does not bypass project access or model consent. An explicit shared **D** scheme preserves the ordinary build/test entry after adding the trial scheme suppressed Xcode's automatically generated entry; it uses the existing targets and does not change the signing identity. See `docs/RELEASE_FREEZE_TRY.zh-CN.md` for the delivery status; a successful build is not an observed Xcode Run.

The optional `ChatPython.dengine` is a separate WASI resource, not the native Python environment used by model engines. It contains fixed CPython 3.14.8 compiled for WASI and Wasmtime 49.0.2 running the Pulley interpreter. To prepare it, use the official CPython `Tools/wasm/wasi` build with WASI SDK 24.0, then use the prepared Python 3.12 interpreter to run `python3.12 -B tools/chat-python/package_runtime.py --cpython-source <built-source> --wasmtime-c-api <matching-full-C-API> --destination <new-absolute-package-path> --identity <existing-development-identity-SHA>`. Verify the fixed archives against the provenance recorded in the task evidence before building; the packager checks versions but does not download or prove archive authenticity. It preserves upstream licenses and uses the existing signing identity for the child helper; App Sandbox remains enabled.

Add that package as the `ChatPython.dengine` source in the existing resource preparation configuration and prepare a **new** resource set with `scripts/prepare-development-resources.py`. Set `D_DEVELOPMENT_RESOURCES` to that prepared directory once; normal Xcode builds then validate and embed it, without manually patching the App or rebuilding Python on each Run. The current prepared set and exact successful commands are linked from the trial guide/task evidence. The helper has sandbox inheritance and is intended to run under the App, not as a standalone signed command. Missing Python resources produce a visible preparation error; they never fall back to executing user code with host Python.
