## 项目总结：基于 MLX Swift 的统一本地生成式 AI 推理与应用平台

### 1. 项目定义与核心哲学

本项目旨在构建一个基于 **MLX Swift** 框架的原生 macOS 应用。其核心定位是一个 **“健壮的模型加载器”** 与 **“统一推理平台”**。项目哲学强调 **以模型文件为中心**：用户提供 Safetensors 格式的模型权重文件，应用负责适配、加载并高效运行。它不预设模型的具体形态，而是追求对主流开源生成式模型（图像、文本、音频、视频）的广泛兼容，以及对各种微调技术（LoRA、ControlNet 等）的原生支持。最终目标是满足专业创作者对 **全精度、无量化、大参数规模** 模型的高标准生成需求，同时通过深度集成的 AI 助手，为不同技术水平的用户提供从“开箱即用”到“精细控制”的全频谱体验。

### 2. 核心功能清单

应用功能将围绕模型的加载、配置、运行与辅助展开，划分为以下核心模块：

- **模型发现与管理**：
    - **动态加载**：支持从本地文件系统加载 Safetensors 格式的模型权重 。
    - **Hugging Face 集成**：内置 Hub 浏览与下载功能，支持通过模型 ID 直接拉取 。
    - **元数据解析**：自动读取模型配置文件（如 `config.json`），识别模型架构、精度、依赖的 Tokenizer 等关键信息 。
    - **量化与转换**：提供模型量化选项（如 4-bit、6-bit、8-bit），并支持将非标准格式模型映射到已知架构 。

- **生成任务执行**：
    - **多模态生成**：支持 Text-to-Image、Image-to-Image 、Text-to-Video 等主流任务。
    - **参数级控制**：为高级用户提供完整的生成参数调节界面（Seed、Steps、Guidance Scale、采样方法等）。
    - **LoRA 与微调**：支持加载一个或多个 LoRA 适配器，并允许用户在界面中调整其影响权重 。
    - **ControlNet 与引导**：支持以 ControlNet 等条件控制模型进行生成 。
    - **推测解码**：可选支持草稿模型进行推测解码，以提升生成速度，同时具备内存资源检测能力以避免 OOM 。

- **统一推理引擎**：
    - **基于 `mlx-lm` 的核心**：所有文本和多模态模型的核心语言部分，均统一基于 `mlx-lm` 的实现，确保性能与特性（如提示缓存）的一致性 。
    - **可插拔视觉编码器**：采用类似 LM Studio `VisionAddOn` 的架构，将视觉编码部分实现为独立插件，在需要时加载，将图像编码为语言模型可理解的嵌入 。
    - **内存规划与优化**：
        - 实现精确的 KV Cache 及 Attention WorkSpace 内存占用量计算器，基于模型配置（层数、头数、维度等）进行估算 。
        - 提供 Wired Memory 的精细控制策略（如 `.stacked` 模式），以支持并行推理并确保内存安全 。
        - 研究并规划对 **内存映射（Memory-Mapped）加载** 的支持，以实现远超物理内存容量的模型加载（Out-of-Core execution） 。

- **深度集成 AI 助手**：
    - **系统级嵌入**：AI 助手并非独立对话框，而是作为操作系统级的服务，可随时唤起以理解用户意图、解释软件功能或提供操作建议。
    - **多模态交互**：助手具备视觉能力，可“查看”当前生成的图像，理解用户对图像的反馈（如“太暗了”、“构图往左一点”），并将其转化为对生成参数的精准调整或提示词修改 。
    - **工作流编排**：助手能够理解用户的高级目标（如“用这张图做参考，生成一个赛博朋克风格的视频”），并将其拆解为具体的、可执行的模块调用序列，自动构建工作流 。
    - **模型即插即用**：AI 助手自身的模型也是可插拔的。在低功耗场景，可调用运行于 ANE 上的 Core ML 模型；在追求性能与灵活性的场景，则无缝切换至 MLX 后端运行更大参数的模型。此过程对用户完全透明 。

### 3. 核心需解决的技术问题

1.  **模型兼容性与适配**：如何为架构日益复杂的开源模型（如 Mamba、MoE、混合架构）设计一个可扩展的加载与适配机制，避免硬编码 。
2.  **内存资源管理与调度**：如何在有限的统一内存中，安全、高效地调度多个大模型（基础生成模型、多个 LoRA、AI 助手模型）以及巨大的 KV Cache，并支持并发推理 。
3.  **并发安全**：鉴于 MLX 操作并非线程安全，如何在 Swift 6 的严格并发模型下，利用 Actor 封装模型实例，确保在多任务环境下不发生数据竞争 。
4.  **可扩展的模块化架构**：如何设计一套低耦合、高内聚的模块化架构，使得添加对新模型类型（如音频）、新微调技术（如 DoRA）的支持时，无需重构核心代码 。
5.  **AI 助手的深度集成与上下文理解**：如何将 AI 助手与软件状态（当前加载的模型、历史生成图像、用户参数设置）深度绑定，使其具备真正的上下文感知能力，并能执行跨模块的操作 。

### 4. 模块化架构设计

项目采用分层与微内核相结合的架构，确保可扩展性与稳定性。

- **表现层 (Presentation Layer)**
    - **技术选型**：SwiftUI
    - **核心职责**：负责所有用户交互与界面渲染。
    - **关键组件**：
        - **主视图**：包含参数面板、图像画布、历史记录画廊。
        - **模型浏览器**：用于浏览本地和 Hugging Face 模型的界面。
        - **AI 助手对话浮层**：嵌入主界面的、用于与 AI 助手交互的界面。
    - **设计要点**：所有界面元素均通过 `@StateObject` 或 `@Observable` 与逻辑层的 ViewModel 绑定，自身不包含任何业务逻辑。严格遵守 Swift 6 并发安全规则，所有 UI 更新均在 `@MainActor` 上执行 。

- **应用逻辑层 (Application Logic Layer)**
    - **技术选型**：Swift `Actor` / `ViewModel`
    - **核心职责**：协调表现层与模型服务层，管理应用状态，处理用户事件流。
    - **关键组件**：
        - **`MainViewModel` (`@MainActor`)**：管理全局应用状态（当前模型、任务队列、生成历史）。接收 UI 事件，调用相应的 Model Service。
        - **`ModelLoadingActor`**：封装所有模型加载逻辑，包括从磁盘读取、量化、适配器融合等。确保加载过程是线程安全的。
        - **`InferenceCoordinatorActor`**：管理推理任务的并发执行。负责任务排队、内存资源检查、调用底层的 MLX Engine 进行推理，并处理推测解码等高级调度策略 。
    - **设计要点**：关键组件均设计为 `Actor`，以隔离状态，防止并发访问。Actor 之间通过异步方法进行通信。

- **模型服务层 (Model Service Layer)**
    - **技术选型**：Swift Protocol + Factory Pattern
    - **核心职责**：为应用逻辑层提供统一的、面向任务的接口，屏蔽底层模型实现的差异。
    - **关键组件**：
        - **`TextGenerationService`**：提供 `generate(prompt:parameters:) -> AsyncStream<String>` 接口。
        - **`ImageGenerationService`**：提供 `generate(prompt:image:parameters:) -> AsyncStream<Image>` 接口。
        - **`VisionLanguageService`**：提供 `answer(prompt:image:) -> String` 等接口，供 AI 助手调用。
    - **设计要点**：通过 Protocol 定义服务契约。每种具体模型（如 Flux 模型、Qwen-VL 模型）都有对应的 Service 实现。应用逻辑层仅依赖于 Protocol，不依赖具体实现。

- **模型适配层 (Model Adaptation Layer)**
    - **技术选型**：MLX Swift, `ModelAdapterFactory` 
    - **核心职责**：这是整个架构的“心脏”，负责将抽象的模型文件转化为可执行的 MLX 计算图。**此为项目核心复杂度的聚集地，也是“可扩展性”的关键。**
    - **关键组件**：
        - **`ModelAdapterFactory`**：根据模型配置（如 `model_type`），动态创建并返回相应的 `ModelAdapter` 。
        - **`ModelAdapter` (Protocol)**：定义了模型必须实现的核心方法，如 `loadWeights()`、`forward()`、`newCache()` 。
        - **具体 `ModelAdapter` 实现**：为每种模型架构（如 `FluxAdapter`、`QwenVLAdapter`、`MambaAdapter`）提供一个实现类。这些类内部包含了对 MLX 网络的精确构建和操作。
        - **`VisionAddOn` (Protocol)**：对于多模态模型，视觉部分被封装成独立的 `VisionAddOn`。核心文本 `ModelAdapter` 在需要时调用 `VisionAddOn.computeEmbeddings()` 来融合图像信息 。
        - **`LoRALinear` / `QLoRALinear`**：MLX Swift 已提供的模块，可在模型加载时动态替换原线性层，实现 LoRA 融合 。
    - **设计要点**：此层的目标是 **“一切皆可插拔”**。新架构的支持，意味着添加一个新的 `ModelAdapter`；新微调技术的支持，意味着添加新的层替换模块；新模态的支持，意味着添加新的 `AddOn`。所有核心框架代码（如调度、内存管理）均不感知这些变化。

- **硬件抽象层 (Hardware Abstraction Layer)**
    - **技术选型**：MLX Core, Metal Performance Shaders
    - **核心职责**：由 MLX 框架原生提供。负责将计算任务调度到 GPU、CPU 或 ANE，并管理统一内存的分配与访问。本项目与此层的交互主要通过设置 MLX 的内存分配策略（如 Wired Memory Limit）来实现 。

### 5. 关键技术细节与实现考量

- **内存规划的精确计算**：借鉴社区对 Qwen3-Next 等复杂模型的 KV Cache 和 Attention WorkSpace 的计算方法，实现对内存占用的预估。这不仅是性能优化，更是功能保障（防止 OOM），并为未来的内存调度器提供决策依据 。
- **内容感知的前缀缓存**：针对多模态任务，实现基于图像内容哈希（而非文件路径）的 Prefix Cache。对于重复出现的图像，可直接复用其视觉嵌入和 KV Cache 状态，大幅降低延迟 。
- **与 AI 助手的 MCP 集成**：将 AI 助手视为一个外部 MCP Client。应用自身需要实现一个 MCP Server，通过标准协议暴露其内部功能（如“调整参数”、“加载模型”、“运行工作流”）。这使得助手能以极其灵活的方式与核心引擎交互，且与助手所用的具体模型解耦 。
- **渐进式启动策略**：初期版本优先确保核心功能的稳定性和架构的正确性，可使用 `InferenceCoordinator` 的串行调度模式。待基础稳定后，再逐步引入并行推理、推测解码、On-disk Streaming 等高级优化特性 。这完全符合“先实现核心功能，再优化性能”的规划。
