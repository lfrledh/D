# D：阶段规模、模型分工与检查点

规划日期：2026-09-06。以下是工程估算与建议，不是固定报价、期限承诺或订阅额度保证。前 3–5 个真实工作包完成后校准一次；产品范围变更时重新估算。

## 估算范围

D 的长期目标是面向专业创作者、兼顾初学者的原生 Mac 本地 AI 推理工作站。它是一项持续演进的产品，不以支持所有模型、所有模态或达到 Photoshop 的全部编辑能力作为首版完成条件。

本次首版估算假设：复用上游 MLX 与成熟模型实现；先支持一类文本模型和一至两类图像模型；一套受支持的 Apple Silicon/macOS 基线；简单模式与专业模式共享任务、资源和工作流语义。图生图、遮罩、LoRA 按实际后端能力挑选，不能默认通用支持。

首版范围暂不包括：任意 ComfyUI 工作流和自定义节点兼容、通用模型文件自动识别并执行、音频/视频全套、第三方插件市场、训练平台、完整绘图编辑器。它们可以后续加入，但每一项都需要独立估算。

当前代码约 6 千行 Swift（含本地测试和清单，不含第三方依赖），属于原型与框架基线。代码量不是完成度：真实推理、内存表现、作品持久化和发布质量尚有大量验证工作。新 runtime 的测试不能证明旧 MLX 后端已经解决取消或并发问题。

## 分阶段规模

“工作包”指有可观察结果、有限改动范围、独立验收标准的一组改动；可能涉及数个关联文件。它不是函数数量，也不等于一次模型调用或一天。复杂包应在开始前继续拆小。

| 阶段 | 可验收成果 | 初步工作包数 | 主要难点 |
| --- | --- | ---: | --- |
| 0：框架基线 | 契约、运行生命周期、确定性测试、原应用构建、架构决策 | 当前检查点 | 新旧边界准确、无虚假完成声明 |
| A：真实推理核心 | 一个真实 MLX 文本后端接入；排队、取消、卸载、错误、内存测量；可重复运行的验证入口 | 4–6 | 任务所有权、GPU 工作结束、版本差异、16 GiB 基线 |
| B：首条图像链路 | 一种明确选定的模型完成生成、参数传递、进度、产物与失败处理 | 5–8 | 模型正确性、峰值内存、数值与速度、图像生命周期 |
| C：可日用 Alpha | 模型管理、简单/专业参数面板、任务队列、项目与生成历史、保存恢复 | 8–12 | 从模型安装到作品保存的完整体验、SSD 权限与断连 |
| D：专业 Beta | 选定的高级控制、批量与预设、两三个真实创作工作流；简单入口与工作流共享执行层 | 10–18 | 图数据类型、资源复用、编辑状态、可复现记录 |
| E：可发布 1.0 | 恢复与诊断、兼容与性能、可访问性、新手引导、签名打包、真实用户反馈修正 | 8–15 | 异常场景覆盖、硬件矩阵、交付质量 |

A–C 合计约 17–26 个工作包，对应有限范围 MVP；A–E 合计约 35–59 个工作包，对应收敛范围的 1.0。完整专业节点编辑器、广泛模型生态适配与完整图像编辑能力会显著扩大 D、E 阶段，不能默认为已包含。

粗略对照熟悉 Swift/MLX 的工程师投入，MVP 约 2–4 人月，收敛的 1.0 累计约 6–12 人月。这里的“人月”描述传统工程规模，并非 AI 协作的日历工期：AI 可并行实现和检索，但真实模型调试、设备验证、产品判断和用户反馈不会按生成速度等比例缩短。

自主代码与测试的量级可暂按 MVP 1.5–3.5 万行、1.0 4–9 万行理解，误差很大，且重用成熟后端可能明显减少。不得将这个数字用作产出目标，也不得据此换算 token 或 Pro 使用额度。

## Pro 与 Astra Ultra 的判断

使用订阅额度持续、分阶段推进有限范围首版是合理方案；没有依据承诺一个额度周期内完成全部功能，或保证全程 Astra Ultra 不遇到限额。一次账户用量快照无法说明每项工程工作的成本，也不能预测之后的返工。

OpenAI 官方说明，用量与模型、推理强度、上下文、工具调用、检索和缓存有关；订阅提供的消息区间不是固定消息上限。API key 调用另按 API 计费，不能当作已包含的 Pro 额度。来源：[Pricing](https://learn.chatgpt.com/docs/pricing)。

官方模型文档将 Ultra 描述为通过子代理并行处理复杂任务；它适合可拆分的复杂工作。提高推理强度通常增加耗时和 token，大部分任务不需要 Max/Ultra。没有在本次核对的官方资料中发现可以套用到 D 的固定 Ultra 用量倍率。来源：[Models](https://learn.chatgpt.com/docs/models)。

工程建议：强模型优先处理架构、并发、MLX 生命周期、跨层故障定位和关键集成验收；普通实现可以按任务风险降低模型或推理强度。不能只比较单次生成价格：便宜实现如果导致多轮高成本返工，总成本可能更高。

| 工作 | 建议起点 | 升级条件 |
| --- | --- | --- |
| 架构、资源/并发所有权、真实推理疑难问题 | Astra；难题用高推理强度，可独立并行时用 Ultra | 需要实验而非更多推理时，先补证据 |
| 边界明确的服务实现、SwiftUI 业务、持久化与普通测试 | Terra 或 Sol，按首次样本表现选择 | 契约跨层变化、难复现错误或反复不通过 |
| 机械转换、确定性样板、文档和局部格式调整 | Luna 或其他经济模型 | 任务实际需要产品判断或隐含状态推理 |
| 关键工作包合并验收 | 强模型结合构建、测试、运行证据 | 不能以代码审阅替代真实行为验证 |

这张表是路由建议，不代表已经更改用户的模型设置、启动付费 API 调用或部署了自动模型路由系统。

## 比“每个函数填空”更合适的协作方式

保留用户设想中的优势：强模型定义边界，经济模型实现，强模型验收。把分工单位从函数提高到小型行为工作包。

若提前逐函数写完整设计，容易重复代码、冻结过早抽象，并在 API、依赖或产品变化时同时维护两套描述。一个函数局部正确，也不保证取消、资源释放和恢复等跨函数行为正确。

采用以下流程：

1. 架构者先给出接口草案、状态转换、不变量、失败语义和验收场景；只定义近期要做的工作包。
2. 实现者读取相关源码、ADR 和工作包，在限定范围内完成关联改动、必要测试与说明；可调整私有辅助函数。
3. 构建与行为验证给出客观结果；涉及 MLX 的改动额外验证真实模型，不以 fake backend 代替。
4. 审阅者检查跨层契约、竞态、取消、资源回收和需求符合性。若实现暴露接口缺陷，先修订设计，而不是强行填满旧模板。
5. 验收后保存一个可回溯的 Git 检查点。下一包从已验证状态继续。

模板见 [TASK_SPEC_TEMPLATE.md](TASK_SPEC_TEMPLATE.md)。先用 Markdown、Swift 接口和测试即可，不必先开发一个复杂的多模型编排平台。

## 额度校准

选取 3–5 个有代表性的真实工作包，例如真实 MLX 适配、取消验证、模型元数据、项目保存恢复和一块参数 UI。记录：模型与推理设置、任务边界、开始/结束用量快照、运行时间、审阅返工次数、最终验收证据。

账户额度在多个任务间共享，后台或并行任务会污染归因；跨重置周期的差值不能直接比较。小任务的百分比读数有取整误差，应按一组任务观察。订阅记录用量百分比；如未来明确使用 API，再另记实际 token 和账单，不混用口径。

按“每个验收通过的工作包的总成本”比较模型策略，并每阶段重新估算剩余工作。不要用单次生成成本或总代码行数判断哪种方案更省。

## Git 检查点

用户已授权在阶段成果完整、验证通过时提交并推送，不需要为每次保存重复确认。当前范围以工作分支保存，不包含自动合并主分支、强制推送或删除远程历史。

最初框架检查点（86a3807）包含：外盘开发环境与 Debug 构建修复、历史材料、架构研究与 ADR、新 DInference/DRuntime 框架及 16 项确定性测试。当时旧应用构建已通过；新 runtime 尚未接入真实 MLX 后端，未下载或验证模型权重。

该检查点仍有六个 Git 子模块，已先推送 ImageInference 编译修复，再推送主仓库更新的引用。之后 6457418 将六个源码树原样纳入主仓库，来源和 SHA 见 docs/history/SUBMODULE_PROVENANCE.json；普通 HTTPS 检出已通过核心测试和旧应用构建。真实后端、固定模型与 CLI 的后续状态见 [MLX 参考实现指南](MLX_REFERENCE_GUIDE.zh-CN.md)，不能继续将最初检查点的限制作为当前事实。

后续检查点按可验收行为保存，例如“真实文本推理和取消验证通过”“首条图像生成闭环完成”“项目可保存恢复”。避免每个函数推送，也避免积累大量无关变更才保存。每次交付说明对应提交、验证结果和未验证事项。
